## 📝 Description

Scripts for the Digital Earth Africa project which provide utilities and solutions for data acquisition and monitoring functions to assist with data validation and quality assurance.

### Utilities

Various resources are included with the following structures:

- **deafrica/data**: data acquisition and processing utilities
- **deafrica/monitoring**: data monitoring and reporting utilities
- **scripts**: Miscellaneous utilities and sample notebooks

Sandbox user and cost report destinations, configuration and rollout are
documented under [Sandbox reports](#sandbox-reports).

#### Data Acquisition

Data acquisition scripts are available for the following resources:

- **[ALOS PALSAR](https://global.jaxa.jp/projects/sat/alos/index.html)**: Advanced Land Observation Satellite Phased Array type L-band Synthetic Aperture Radar

- **[CHIRPS](https://www.chc.ucsb.edu/data/chirps)**: Climate Hazards Group InfraRed Precipitation with Station data

- **[Copernicus GLS](https://zenodo.org/record/3939038)**: Copernicus Global Land Service Land Cover 100m

- **[Copernicus CCI](https://cds.climate.copernicus.eu/cdsapp#!/dataset/satellite-land-cover?tab=form)**: 300m Land Cover Classification ESA Climate Change Initiative, Copernicus

- **[GMW](https://data.unep-wcmc.org/datasets/45)**: Script generates mangrove extents mapped by Global Mangrove Watch over Africa in cloud optimized rasters at 0.001 0.001 spatial resolution.

#### Monitoring

The following elements outline available monitoring utilities and their functions:

- **Check dead queues**: Monitor DEAfrica dead queues, with an option of Slack alert.
- **Landsat gap filler** : Transfer scenes that are missing in DEAfrica from USGS S3 bucket. A list of missing scenes is generated by the gap report process and used to fill gaps.
- **Landsat gap Report**: Check differences across satellites Landsat 8, 7, and 5 between USGS bulk file and DEAfrica's inventory bucket. As per result, gap report will generate a JSON file within a list of missing and orphan scenes.
- **Sentinel 2 gap filler**: Transfer scenes that are missing in DEAfrica from Element-84 inventory bucket. A list of missing scenes is generated by the gap report process and used to fill those gaps.
- **Sentinel 2 gap Report**: Check differences between Element-84 inventory bucket and DEAfrica's inventory bucket. As per result, gap report will generate a JSON file within a list of missing and orphan scenes.

## Sandbox reports

The weekly user report covers the previous complete Monday-to-Sunday week in
UTC. It runs on Monday at 00:10 UTC (03:10 Nairobi time), allowing time for login
events to arrive. The weekly cost report contains Kubecost data for `lastweek`
and continues to run on Monday at 00:00 UTC (03:00 Nairobi time).
The production monthly user report remains a full account snapshot on the 25th.

### Weekly report contents

The weekly Excel workbook contains four sheets:

| Sheet | Contents |
| --- | --- |
| `Summary` | Reporting dates, unique users with recorded sign-ins, sign-in count, new registrations and total accounts at report generation |
| `Active users` | Users with recorded Cognito sign-ins in that week, plus their sign-in count and first/last sign-in within the week |
| `New users` | Accounts created during that week and still present when the report runs |
| `All users` | Full current account list and groups for reference |

For example, a run on 9 November 2026 covers 2 November at 00:00 UTC up to,
but excluding, 9 November at 00:00 UTC. Manual reruns during that calendar week
cover the same complete reporting week. Archive filenames retain their UTC run
date; the workbook's summary states the actual reporting period.

Activity is defined as recorded sign-ins. Existing sessions that continue without
a new sign-in are not measured, and this is not notebook runtime or session
duration. Activity comes from the existing Cognito post-authentication Lambda's
CloudWatch login records. The current `custom:last_login` value is retained in
the reference data but is not used to reconstruct weekly activity, since a later
login overwrites it. `UserLastModifiedDate` is not an activity indicator.
The existing login records do not contain an app client ID. The pool also serves
Argo and Grafana, so this history describes shared-pool sign-ins; it cannot prove
which sign-ins were specifically to Sandbox. The summary states that scope.
Sandbox-only reporting would require application-identifying login records.

The active-user list includes usernames seen in the logs even if their account
has since been removed; `AccountPresentAtReport` identifies these rows, whose
other account details are unavailable. New-user and total-account counts reflect
accounts still present when the report is generated. The summary flags missing
or invalid registration dates.

The monthly report keeps its existing single-sheet full-account snapshot. Its
contents are not filtered to monthly activity.

### Report destinations

Configure separate Google Drive destination folders for users and costs. Their
names can differ from the illustrative names below; the configured folder IDs
determine the destinations.

```text
Users/
  Users_prod_latest.xlsx
  Users_prod_monthly_latest.xlsx
  2026/
    Users_prod_2026-11-09.xlsx
    Users_prod_monthly_2026-11.xlsx
  2027/
    Users_prod_2027-01-04.xlsx
    Users_prod_monthly_2027-01.xlsx

Costs/
  2026/
    sandbox-weekly-cost-report-prod-2026-11-09.csv
  2027/
    sandbox-weekly-cost-report-prod-2027-01-04.csv
```

Each run finds or creates its year folder using the UTC date captured at the
start of the report. A rerun updates the existing dated file in that folder.
Both weekly and monthly user reports update their own permanent latest file
after their archive has uploaded successfully:

- Weekly updates `Users_prod_latest.xlsx` and saves a dated weekly archive.
- Monthly updates `Users_prod_monthly_latest.xlsx` and saves an archive labelled
  `Users_prod_monthly_YYYY-MM.xlsx`.

Weekly and monthly runs update separate latest files. Each latest file keeps its
Drive file ID and link. Older weekly and monthly archives remain available when
a new week or month is published. A rerun within a month updates that month's
archive, rather than creating another copy. If an upload fails, the job fails
and an existing latest file remains available.

Weekly latest contains the most recent successful weekly workbook, including its
summary, activity lists and full reference sheet. Monthly latest contains the
most recent successful monthly full-account snapshot. Manual runs of each
workflow update its own latest file when latest publication is enabled.

Dev reports use `dev` in their filenames, including `Users_dev_latest.xlsx` and
`Users_dev_monthly_latest.xlsx` when running a monthly report manually.
The upload code also supports running without an environment suffix.

Cost S3 archives use:

```text
s3://deafrica-cost-usage-reports/sandbox-weekly-report/2026/sandbox-weekly-cost-report-prod-2026-11-09.csv
```

`REPORT_PREFIX` remains configurable; the script appends the run year. S3-only
cost uploads remain supported with `REPORT_UPLOAD_TARGET=s3`.

### Workflow configuration

Both report scripts use the shared Google Drive upload helpers in
`deafrica/utils.py` for year folders, archives and latest-file updates.

The `datakube-apps` weekly user CronWorkflows and production monthly user
CronWorkflow use the shared `sandbox-users-report` WorkflowTemplate. The
template receives the environment, image tag, `report-frequency` and
`publish-latest` settings as parameters. Both weekly and monthly workflows set
`publish-latest` to `"true"`. Weekly workflows use `report-frequency: weekly`;
the monthly workflow uses `report-frequency: monthly`, which selects its monthly
archive name and its separate monthly latest file.
The shared template defaults to latest publication being `"false"`, so manual
runs of the template only archive a snapshot unless explicitly configured to
publish latest. It also accepts an optional `email_address` for an attachment.
A shared mutex per environment serializes weekly, monthly and manual user runs
to avoid simultaneous folder or latest-file creation.

The CLI uses the same default: `sandbox-users-report` saves a dated snapshot.
Scheduled workflows enable latest publication using `REPORT_PUBLISH_LATEST=true` or
`--publish-latest`. Use `--no-publish-latest` to explicitly disable it.
Monthly runs use `REPORT_FREQUENCY=monthly` or `--frequency monthly`. For a manual
monthly run that also updates monthly latest, use
`sandbox-users-report --frequency monthly --publish-latest` with the normal
credentials and folder configuration.

The `processing/sandbox-weekly-report-google-drive` Kubernetes Secret must
contain these keys in each environment before enabling the updated workflows:

| Key | Purpose |
| --- | --- |
| `credentials.json` | Existing Google service-account credentials |
| `folder_id` | Cost-report destination folder ID |
| `user_folder_id` | Separate user-report destination folder ID |

Production Terraform already defines all three keys, using
`/<cluster_id>/sandbox/google-drive.user.folder-id` for the user destination.
Dev has no equivalent Google Drive secret resource in the checked-in Terraform;
ensure its existing secret is provisioned with `user_folder_id` before deploying
the dev workflow change. The user template's `google-drive-folder-key` parameter
defaults to `user_folder_id` and can select a differently named secret key.

The service account needs access to both destination folders, including creating
folders and uploading/updating files. Check that intended readers have access to
the user folder and its new files.

Weekly reports also require `cognito-idp:DescribeUserPool`,
`logs:DescribeLogGroups` and `logs:FilterLogEvents`. The existing dev and production
`role_platform_admin.tf` files add these read-only permissions, with log-event
access scoped to the environment's post-authentication Lambda log group. Apply
those Terraform changes before running the updated weekly report. The script
discovers the Lambda from the configured user pool; no extra secret keys or
login-tracking changes are required.

Verify that the log group predates the reporting week and retains the whole
week plus the reporting delay (at least 14 days, or no expiry, is suitable for
normal weekly runs). If the trigger/log group is absent, retention is insufficient
or log access fails, the weekly job fails before publishing the workbook or
updating latest. It does not silently substitute last-login values or publish
zero activity. Log retention and creation time cannot detect arbitrary historical
gaps, so confirm real login records and collection before production rollout.

### Rollout and verification

1. Verify the destination IDs are different, the secret keys exist, and the
   service account can access both folders.
2. Merge and build the `deafrica-scripts` image containing these changes. Its
   existing CI publishes `latest` after the tests pass.
   Apply the dev/production Terraform read permissions before enabling weekly
   activity reports, and verify the authentication log history covers the week.
3. Deploy the matching `datakube-apps` changes through the normal GitOps process.
   An explicit `image-tag` can be supplied for a controlled rollout or manual run.
4. Run the weekly user and cost workflows. Check the weekly workbook's four
   sheets, reporting period, counts and logins against sample source events.
   Check dated files under the current year,
   the latest user file at the user-folder root, and the cost S3 year prefix.
5. Rerun weekly users and check that the latest link stays unchanged and the dated
   file is updated rather than duplicated. Run the monthly user workflow and
   confirm it saves `Users_prod_monthly_YYYY-MM.xlsx` in the year folder and
   updates `Users_prod_monthly_latest.xlsx` without changing the weekly latest
   file. Rerun monthly within the same month and confirm it updates the same
   archive and preserves the monthly latest link. A later month's run must keep
   earlier monthly archives available.
   Check access using an intended reader.

These changes organise new report output. Existing files in the old flat
folders or S3 prefix are not automatically moved, and existing duplicates are
not deleted. Their relocation is a separate migration so access and any links
to historic reports can be checked first.

### Focused tests

```sh
pytest deafrica/tests/test_sandbox_cognito_userpool_report.py \
  deafrica/tests/test_sandbox_weekly_cost_report.py
```

The tests use simulated Drive storage, rather than uploading user data, and
exercise complete-week boundaries, login-history pagination and deduplication,
registration filtering, incomplete-history failures, repeat runs, stable latest
links, failed uploads, monthly and year rollover, preservation of history and
independent weekly/monthly latest files.

API references: [Drive file lookup](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list),
[Drive file updates](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update),
and [Argo workflow synchronization](https://argo-workflows.readthedocs.io/en/latest/synchronization/).
Weekly activity uses [Cognito post-authentication events](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-post-authentication.html)
and [CloudWatch log pagination](https://docs.aws.amazon.com/boto3/latest/reference/services/logs/paginator/FilterLogEvents.html).

## ⚙️ Setup & Run

Clone the main project repository from Github.

```shell
$ git clone https://github.com/digitalearthafrica/deafrica-scripts.git
```

## Building locally

```shell
$ cd deafrica-scripts
$ docker build -t Deafrica-Scripts
```

## Download Image from the repository

```shell
$ docker pull digitalearthafrica/deafrica-tools
```

## Local Development

Local installation and development will require development dependencies `requirements.txt`.

From the project root directory, use pip to install dependencies as follows:

```shell
$ pip install -r requirements.txt
$ pip install -e .
```

## 📝 Tests

Running tests will require development dependencies `requirements-test.txt`.

From the project root directory, use pip to install test dependencies as follows:

```shell
$ pip install -r requirements-test.txt
$ pytest .
```

## ⚙️ GitHub Actions

Any changes pulled to any branch will be tested and have the formation checked by black.

A Merge will result in the creation of a new test image on Docker and 45 min later replicated on our AWS ECS.
